### 3. Go 값 검사기가 Scalars의 실제 크기를 잘못 사용한다. 중요도 중간

`goval.py`의 Scalars 크기는 16이다.
16은 SSZ 직렬화 크기다.
amd64 Go 객체 크기는 24이며, bool 필드는 오프셋 16에 있다.
근거: `fv/kraken/lean/tools/wit/goval.py:38`, `fv/kraken/target/types.go:5`.

Go 1.26.3에서 크기 24, 정렬 8, bool 오프셋 16을 확인했다.
amd64 교차 빌드에서도 `unsafe.Sizeof`가 정확히 24라는 컴파일 검사를 통과했다.
재현 파일: `E/ReviewGoLayout.go`.

이 차이는 실제 증인에 영향을 준다.
주소 구간은 끝 주소를 포함하지 않는다.

| 증인 | 실제 객체 구간 | 문제 |
| --- | --- | --- |
| `WitScA` | `[0x10028,0x10040)` | 메모리 블록은 `0x10039`에서 끝남 |
| `WitScM` | `[0x10028,0x10040)` | dst가 `0x10039`에서 시작하여 마지막 패딩 7바이트와 겹침 |
| `WitNeM0/1/16`의 Scalars | `[0x10080,0x10098)` | ListU64 객체가 `0x10091`에서 시작하여 패딩과 겹침 |

근거: `fv/kraken/lean/Fk/WitScA.lean:36`, 같은 파일 `:42`,
`fv/kraken/lean/Fk/WitScM.lean:42`, `fv/kraken/lean/Fk/WitNeM16.lean:53`.
나머지 두 Nested 증인도 같은 배치를 사용한다.

검사기의 크기만 리뷰 사본에서 24로 해석하면 `WitScA`가 즉시 실패한다.
객체와 버퍼 구간을 별도로 대조하면 나머지 겹침도 나온다.
기록: `E/reprove-fix-go-overlaps.json`.
Lean에서도 블록 길이 57과 겹치는 주소 관계를 확인했다.
근거: `E/ReviewReproveFixAstra.lean:43`.

사용 필드의 분리 조각은 서로 겹치지 않는다.
따라서 기존 기계어 정리와 증인이 거짓이라는 뜻은 아니다.
하지만 온전한 Go 객체를 갖춘 증인이라는 주장은 틀렸다.
이는 보고서가 추가한 완료 요소 6 자체의 미충족이다.
근거: `fv/kraken/REPORT-1b-reprove-fix.md:44`, 같은 파일 `:168`.

수정: 직렬화 크기와 Go 객체 크기를 구분하라.
Scalars 뒤의 패딩을 확보하고 후속 객체와 dst를 이동하라.
객체 크기, 정렬, bool 값, 겹침을 검사 범위에 추가하라.
허용한 별칭과 금지한 겹침도 구분하라.

### 4. FmtErrorfWC는 여전히 실제 Go가 만족할 수 없는 넓은 호출을 포함한다. 중요도 높음

오류 객체의 추가는 올바른 개선이다.
그러나 계약은 `fs`를 실제 생성 코드의 형식 문자열로 제한하지 않는다.
앞선 인수 `pre`도 바이트 길이만 제한한다.
근거: `fv/kraken/lean/Fk/Contracts.lean:157`.

유효한 Go 값으로 두 가지 시험을 실행했다.

- `fmt.Errorf("%100000w", errors.New("e"))`의 결과 문자열은 100000바이트다.
- 계약의 예산식은 이 입력에 8201바이트를 준다.
- `fmt.Errorf("%v: %w", changing{}, errors.New("e"))`는 앞선 인수의 `String()`을 호출한다.
- 그 메서드가 전역 변수를 바꾸면 계약의 임의 프레임 보존과 충돌한다.

재현: `E/ReviewFmtBounds.go`, `E/reprove-fix-fmt-runtime.log`.
이 두 호출은 실제 생성 코드의 호출은 아니다.
하지만 현재 계약이 양화하는 형식과 인수 범위에는 들어간다.
따라서 생성 코드의 좁은 호출만 필요하다는 이유로 현재 보편 계약을 실제 Go에 적용할 수는 없다.

첫 시험은 문서의 예산 신뢰 항목이 모든 허용 형식에 성립하지 않음을 보여 준다.
현재 사후조건은 실제 할당 바이트를 직접 측정하지 않으므로, 이것만으로 Lean 모순을 주장하지 않는다.
두 번째 시험은 유효한 인수에서도 프레임을 변경할 수 있음을 보여 준다.

ListU64에 남은 convT64 문제도 구체적이다.
`WitLuTb`와 `WitLuMa`는 `Heap := fun _ => emp`와 숫자 예산 8271을 쓴다.
`rt_convT64` 모델은 rax에 1만 넣는다.
상자 메모리와 uint64 값은 만들지 않는다.
근거: `fv/kraken/lean/Fk/WitLuTb.lean:136`, `fv/kraken/lean/Fk/RtErr.lean:77`,
`fv/kraken/lean/Fk/RtErr.S:9`.

이는 추상 계약의 비공허성 증인으로는 유효하다.
하지만 8271바이트의 실제 할당 공간과 유효한 `%d` 상자가 있다는 증인은 아니다.
CONTRACTS가 상자 내용의 미증명을 적은 것은 정직하다.
그 상태에서 오류 호출 적용 조건이 완료됐다고 표시하면 안 된다.
근거: `fv/kraken/CONTRACTS.md:103`, 같은 파일 `:105`, `:107`.

수정: 필요한 네 형식 호출로 계약의 범위를 제한하라.
BitVec·BitL은 앞선 인수 없이 errorString 하나만 받게 하라.
ListU64는 첫 인수의 uint64 타입, 상자 내용과 자원을 요구하라.
프레임 보존과 예산은 그 제한된 호출에 대해 적어라.
전체 fmt나 Go 런타임 증명을 지금 요구하는 것은 아니다.

### 5. rodata를 F 밖에 둔다는 문구만으로 ValidateBitlistErrC를 Go에 적용할 수 없다. 중요도 높음

읽기 전용 데이터 영역인 rodata의 메시지를 새 계약의 문제로 밝힌 점은 옳다.
하지만 계약 자체는 여전히 모든 `F`에 양화한다.
그 양화를 좁히는 전제는 없다.
근거: `fv/kraken/lean/Fk/Vbl.lean:68`, `fv/kraken/CONTRACTS.md:104`.

Go의 인수 없는 오류는 기존 문자열을 참조한다.
계약의 결론은 그 메시지를 `ErrStr` 안의 독점 조각으로 새로 꺼낸다.
동시에 원래 `F`도 그대로 보존한다.
`F`가 같은 rodata를 소유하면 두 조각이 겹친다.

리뷰 Lean 파일에서 같은 주소의 1바이트 조각을 두 번 분리 소유할 수 없음을 확인했다.
근거: `E/ReviewReproveFixAstra.lean:34`.
이는 `joint_models`의 모순은 아니다.
모델은 빈 메시지를 선택하므로 이 충돌을 피한다.
근거: `fv/kraken/lean/Fk/RtVbl.S:16`, `fv/kraken/lean/Fk/Vbl.lean:347`.

실제 호출의 `F`를 조심해서 고르는 것과, 모든 `F`에 대한 계약을 Go에서 얻는 것은 다르다.
문서의 조건은 필요할 수 있지만 현재 보편 계약의 정교화 증거가 되지 않는다.
기존 rodata 바이트를 어떤 사전 자원에서 받는지도 명시해야 한다.

수정: 읽기 전용 공유 자원을 별도로 두거나, 메시지 자원을 사전조건에 제공하라.
그 자원이 있는 프레임만 양화하게 하라.
소유권을 옮기는 방식이면 예산과 정적 데이터의 관계도 구분하라.
이전 필수 수정 5는 여전히 부분 완료다.

## 8. 게이트 판정과 필수 수정

게이트 1은 **미통과**다.
직접적인 이유는 다음과 같다.

1. 실제 Lean 값과 다른 값을 링크 검사기가 승인한다.
2. Go 값 완료 열에 객체 크기 오류가 있다.
3. 형식 계약과 rodata 계약의 실제 호출 적용 범위가 아직 형식화되지 않았다.
4. 조합 가능한 사후조건과 중첩 최대 입력 증인이 남았다.

모든 디코더 거부 경로를 반드시 이번 세션에 끝내야만 한다는 판정은 아니다.
선택한 빠른 경로와 명시한 조건에 대한 게이트는 가능하다.
그러나 이미 정한 조건을 충족하지 못한 상태를 조건부 통과로 바꾸면 안 된다.

필수 수정 목록:

1. SHash 주석 제거를 문자열 인식 방식으로 고쳐라. 균형 잡힌 주석 구분자 변이를 추가하라.
2. 형식 상수 전체 값과 모든 참조를 검사하라. 접미 식, 공백 변형, Go 주석 변이를 추가하라.
3. Go 객체 크기를 실제 타입 배치에서 가져와라. Scalars가 들어간 증인의 패딩과 겹침을 고쳐라.
4. fmt 계약을 실제 형식과 인수 타입으로 제한하라. ListU64 상자의 내용과 자원을 연결하라.
5. rodata 메시지의 공유 또는 이전 자원을 형식화하라. 안전한 프레임만 계약이 양화하게 하라.
6. ListC 수용·마샬에 비어 있지 않은 원소와 최대 내부 길이 증인을 추가하라.
7. 선택한 완료 타입의 사후 자원을 보존하라. 전체 조합 증인과 중간 상태 구성을 추가하라.
8. 게이트 표를 실제 검사 범위에 맞춰 고쳐라. “미검사”, “추상 모델”, “Go 값”, “조합”을 구분하라.

1c 전에 닫을 거부 경로의 우선순위:

- Scalars의 bool > 1 거부를 닫아라. 가장 작은 정규 인코딩 거부 기준 사례다.
- BitL 디코더의 ValidateBitlist 오류 반환을 닫아라. 새 오류 계약의 실제 사용 경로를 검사할 수 있다.
- ListC의 원소 오프셋 순서 거부와 비어 있지 않은 원소의 오류 전달을 수작업 기준 사례로 확보하라.

ListC의 나머지 정렬·원소 수 오류와 Nested의 모든 래핑 경로는 1c의 후속 대상으로 둘 수 있다.
그 경우 완료 범위를 표에 남겨라.
ListU64의 네 거부 정리와 수용 정리를 묶는 양방향 정리도 좋은 초기 자동화 대상이다.
해당 정리들이 있다는 사실과 하나의 양방향 정리가 있다는 사실은 구분해야 한다.

## 9. 1c 설계 입력과 브리프

보고서의 18개 입력은 대부분 타당하다.
다음 보완을 넣어라.

| 입력 번호 | 검토와 보완 |
| --- | --- |
| 1 | 세 스택 좌표와 반환 슬롯 관계를 작은 정리로 고정하라 |
| 2 | 공동 Host 검사와 실제 할당 자원을 구분하라. emp 힙의 숫자 예산을 물리 공간으로 세지 마라 |
| 3 | 기호 길이 제한은 구체 배치 생성기에만 적용하라 |

| 7 | 해석된 Lean 식에서 전제를 읽어라. 현재 텍스트 파서의 우회를 기준 사례로 삼아라 |
| 9 | hupd 존재, 전체 조합 증인, 실제 호출자 실행을 각각 완료 항목으로 둬라 |
| 10 | 크기·정렬·패딩·bool·유효 타입 워드를 포함하라. 검사를 건너뛰면 완료로 표시하지 마라 |
| 11 | 오류 객체뿐 아니라 rodata 공유, 상자 값, fmt 형식과 인수 타입을 함께 모델하라 |

| 14 | Go 회귀와 Lean 거부 정리를 함께 갱신하는 방침을 유지하라 |

| 17 | 레이블 불변식의 진입·보존 목표를 별도로 측정하라 |
| 18 | 1시간 7분을 일반 타입 완료 비용으로 외삽하지 마라 |

1c의 고정 기준:

- 생성기 소스 `698c202`와 병합 기준 `2d0150b`를 구분해서 기록하라.
- Go 1.26.3, linux/amd64, GOAMD64=v1, purego, trimpath, CGO_ENABLED=0을 유지하라.
- Kraken `6064eec`, EthLib `8621856`, Lean nightly-2026-09-21을 고정하라.
- Prysm은 v7.1.8, `51b5a75ebbadf05af22bd2601b5baf7a9e99b66d`의 축약 두 타입이다.
- protobuf 필드를 포함한 실제 Prysm 바이너리 증명으로 이름을 바꾸지 마라.
- 현재 범위는 코덱이다. 해시와 임의 위임 타입은 별도 범위다.

근거: `fv/kraken/TOOLS.md:11`, 같은 파일 `:13`, `:15`.

자동화 순서는 다음이 적절하다.

1. Scalars 수용·거부로 정규 인코딩과 값 보존을 고정하라.
2. ListU64의 0·1·16과 growslice 호출 지점을 자동화하라.
3. ListC의 바깥 0·1·4, 내부 0·1·16을 조합한 수작업 사례를 먼저 완성하라.
4. 혼합 길이와 최대 길이에서 오프셋, 힙 소비, 오류 전달을 확인하라.
5. 그 사례를 생성기로 재현하고, 두 호출 조합까지 확장하라.
6. 마지막으로 축약 Checkpoint·AttestationData에 적용하라.

현재의 빈 내부 리스트만 자동화하면 중요한 할당·복사 조합을 건너뛸 수 있다.
1c 작업을 시작할 수는 있다.
다만 이번 결과를 이미 완료된 게이트 1의 기준점으로 쓰면 안 된다.

미확인: 실제 x64 하드웨어 실행과 Go 런타임의 계약 정교화는 확인하지 않았다.
남은 위험: 추상 모델의 비공허성과 일부 Go 값 검사를 실제 Go 실행 전체의 검증으로 해석하면 안 된다.

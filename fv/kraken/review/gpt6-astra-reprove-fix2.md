## 1. 반드시 고칠 발견

### 발견 1. 선언 역할 분류가 Host 바인더와 이름 가림을 구분하지 못한다

위치: `fv/kraken/link/check.py:155`, `:161`, `:162`, `:466`.

검사기는 파일 전체에서 구체 Host 선언을 찾는다.
그 뒤 선언 머리에 정확한 문자열 `[Host]`가 없으면 증인으로 분류한다.
Lean의 실제 인스턴스 인수와 선언 범위를 읽지 않는다.

다음 변이는 모두 링크 검사에서 PASS였다.

- `WitScM`에 `[h : Host]`를 받는 일반 선언을 추가했다.
- `variable  [Host]` 뒤에 일반 선언을 추가했다.
- `{h : Host}`와 `letI := h`를 쓰는 일반 선언을 추가했다.
- `variable [h : Host]`와 `omit h in`을 포함한 section에 일반 선언을 추가했다.

각 선언은 `(z 1)`을 미등록 오프셋 `go_string._+99999`에 놓는다.
이는 구체 증인의 채움이 아니다.
임의 Host에 대한 배치 명세다.

이름 가림도 통과한다.
`def review_bad [Host] (blFmtB : List UInt8) := ...`의 인수는 등록된 상수와 이름만 같다.
검사기는 이 인수를 실제 `Fk.blFmtB`로 취급한다.
따라서 `[0]`을 `go_string._+526`에 놓는 일반 명세도 PASS가 된다.

증거: `E/reprove-fix2-mut-role-named-host.log`, `-role-variable-space.log`, `-role-implicit-let.log`, `-role-omit.log`, `-format-binder-shadow.log`.
선언의 Lean 확인은 `E/reprove-fix2-role.lean`에 있다.
임의 Host 인수가 남는 것을 출력된 선언에서도 확인했다.
역할·이름 가림 변이 5개의 원본 파일 사본도 각각 Lean 검사를 통과했다.

최소 수정은 검증한 선언 이름과 역할을 명시적으로 등록하는 것이다.
일반 선언이 등록된 상수 이름을 다시 바인딩하면 거부해야 한다.
1c에서는 해석된 Lean 선언과 완전한 이름을 사용해야 한다.
현재 문자열 기반 역할 분류를 그대로 일반화하면 안 된다.

현재 제출된 정리에서 이 우회가 쓰였다는 뜻은 아니다.
검사기의 전수 참조 검증 주장이 아직 성립하지 않는다는 뜻이다.

### 발견 2. 새 런타임 데이터 검사 (h)도 식 접미사와 다른 포인터 타입을 허용한다

위치: `fv/kraken/link/check.py:478`, `:488`, `:495`.

`luTW`는 정규식 검색으로 식의 앞부분만 읽는다.
다음 변경이 PASS였다.

```lean
def luTW : BitVec 64 := (label "type__" + 49184).toBitVec + 8
```

실제 정의는 타입 기술자의 중간을 가리킨다.
검사기는 여전히 원래 타입 시작 주소의 Size_와 Kind_를 확인한다.

`StaticBox`는 부분 문자열 존재만 확인한다.
주소에 `+ 8`을 더해 다음 표 항목을 읽도록 바꿔도 PASS였다.
표의 실제 바이트가 정확해도 Lean 식과 표의 연결은 틀릴 수 있다.

ELF 데이터 변이도 PASS였다.
`go:itab.*errors.errorString,error+8`을 다른 `*uint64` 기술자로 바꿨다.
원래 기술자는 `0x4d4a00`이었다.
변이 기술자는 `0x4cbf00`이고 원소 기술자는 `0x4cfce0`이었다.
둘 다 Size_ 8, Kind_ 22이므로 현재 검사를 통과했다.
로그는 이를 계속 `*errors.errorString`이라고 표시했다.

증거: `E/reprove-fix2-mut-typeword-suffix.log`, `-staticbox-suffix.log`, `-itab-wrong-pointee.log`.

`luTW`와 `StaticBox`의 전체 정의를 검사해야 한다.
errorString 타입은 포인터 종류만으로 식별하면 안 된다.
타입 이름, 원소 타입과 필요한 메서드 연결을 검증해야 한다.
또는 이 바이너리의 검증된 데이터와 재배치 관계를 명시적으로 고정해야 한다.

현재 원본 ELF의 타입이 잘못됐다는 발견은 아니다.
변경된 ELF에서도 부정확한 PASS를 주는 검사기 결함이다.
이 변이는 ELF 해시를 바꾼다.
고정된 원본 ELF 해시 자체를 우회한 것은 아니다.

### 발견 3. Go 파서는 `fmt`라는 식별자를 표준 패키지로 오인한다

위치: `fv/kraken/link/golits.go:39`, `:43`, `:46`.
위치: `fv/kraken/link/check.py:437`.

go/parser는 문법을 읽는다.
현재 코드는 import와 식별자의 실제 선언을 확인하지 않는다.

실제 `fmt.Errorf("B: %w", ...)`를 모두 `"B: %v"`로 바꿨다.
같은 파일에 `fmt`라는 지역 구조체를 둔 보조 함수를 추가했다.
그 구조체의 `Errorf` 함수는 nil을 반환한다.
그 호출에만 `"B: %w"`를 남겼다.
링크 검사와 `go build ./fv/kraken/target`이 모두 통과했다.

증거: `E/reprove-fix2-mut-go-fmt-shadow.log`, `-go-fmt-shadow.txt`.

별칭 import, 함수 변수, 상수 형식은 반대 문제가 있다.
현재 수집기는 이를 읽지 않는다.
해당 형식의 다른 직접 호출이 없으면 검사에 실패한다.
다른 직접 호출이 남으면 그 호출 하나로 검사할 수 있다.
이것은 호출 위치별 대응 검사가 아니다.

ELF 검사는 기계어와 바이트의 연결을 보완한다.
그 검사가 현재 Go 소스의 모든 호출과 ELF의 대응까지 증명하지는 않는다.

최소 수정은 허용한 생성 코드 문법과 import를 제한하고 이름 가림을 거부하는 것이다.
범위를 넓히려면 go/types로 호출 대상을 확인해야 한다.
지원하지 않는 호출 모양은 명시적으로 거부해야 한다.

## 3. 계약, 공허성, 신뢰 경계

`joint_models`는 이제 계약 10개다.
인수는 7개이고 Host는 하나다.
모두 같은 `bumpHeap`을 사용한다.
newobject는 같은 레이블의 16바이트 모델이다.
근거: `fv/kraken/lean/Fk/Regress.lean:85`, `:91`.
24바이트와 32바이트 newobject까지 동시에 증명한 정리는 아니다.
그 조합은 각 타입의 별도 증인이 담당한다.

임의 RO·MsgIn에 대한 모델은 모순이 아니다.
fmt 모델은 인수 개수만 보고 rax를 1로 만든다.
메시지를 읽거나 출력 오류 객체를 만들지 않는다.
그래서 모든 자원 인수에 대해 같은 모델이 성립한다.
근거: `fv/kraken/lean/Fk/RtErr.lean:52`, `:80`.
이는 비공허성의 증거다.
Go fmt 구현의 정교화 증명은 아니다.

실제 호출자 인스턴스의 메시지 연결은 확인했다.
`VblMsg`의 rodata 경우는 주소와 바이트를 `vblRO`의 해당 조각에 묶는다.
힙 경우는 `hm = msg`를 요구한다.
`BvMsg`도 `bvRO`의 주소와 `vbvFmt`를 고정한다.
근거: `fv/kraken/lean/Fk/Vbl.lean:76`, `:84`, `fv/kraken/lean/Fk/BvSpec.lean:440`.

독립 Lean 파일의 `vbl_message_owned`와 `bv_message_owned`가 이 연결을 확인한다.
메시지 바이트를 읽을 자원이 실제로 존재함을 분리 논리로 도출한다.
기존의 rodata와 프레임 중복 소유 문제는 이 인스턴스에서 해결됐다.
메시지를 입력 분기와 정확히 연결하지 않는 선택은 현재 비nil 거부 명세에 허용할 수 있다.

`ConvT64C`는 실제 Go의 두 결과 모양을 포함한다.
작은 값은 정적 표를 가리킨다.
큰 값은 8바이트 상자에 저장된다.
모델은 작은 값도 힙에 넣을 수 있다.
이 넓은 결과는 비공허성 모델에 허용된다.
근거: `fv/kraken/lean/Fk/Contracts.lean:91`, `:98`, `:109`.
Go 원본: `$GOROOT/src/runtime/iface.go:400`.

| 경로 | 계산 |

## 8. 게이트와 필수 수정 목록

게이트 1 미통과 자평에 동의한다.

반대로 “크기 정리 11개”는 실제 부족분으로 다시 줄여야 한다.

Scalars와 ListU64를 타입 전체 완료로 표시할 수 없다.
Scalars는 비nil 오류 연결과 Size 사후조건이 남았다.
ListU64는 오류 증인의 Go 타입 자료와 전역 조건이 남았다.
둘의 수용·마샬 조합 증인은 완료라고 표시할 수 있다.
이 구분은 현재 6요소 표와 외부 계약의 의미를 함께 보존한다.

필수 수정은 다음과 같다.

1. Lean 참조 검사의 역할과 이름 해석을 고친다. 발견 1의 변이를 자기 시험에 넣는다.
2. (h)의 전체 식과 타입 동일성을 검사한다. 식 접미사와 다른 포인터 기술자를 거부한다.
3. Go 형식 호출의 실제 대상을 확인한다. 지역 `fmt`와 지원하지 않는 호출 모양을 명시적으로 처리한다.
4. 오류 타입 자료와 전역 불변식을 증인에 연결한다. Scalars에 비nil 거부 정리와 증인을 둔다.
5. goval을 배치 재생성 뒤 실행한다. 값·타입·조각의 미검사를 별도로 집계한다.
6. 남은 사후조건을 보강한다. NeMarshal, ListC 스택, Scalars Size와 필요한 r14 보존을 우선한다.
7. ListC 원소 오프셋 순서와 비어 있지 않은 원소의 오류 전달을 수작업 기준 사례로 닫는다.
8. 게이트 표를 정정한다. 메모리 동일성을 프레임 보존으로 인정하고 추상 증인과 Go 값 완료를 구분한다.

1–5는 1c 생성 결과를 신뢰하는 검사기로 사용할 때 먼저 필요하다.
6–7은 게이트 완료와 일반 조합을 주장하기 전에 필요하다.
8은 현재 보고서에 바로 반영해야 한다.
Go 런타임 정교화와 x64 하드웨어 대조는 별도 신뢰 작업으로 계속 남는다.
